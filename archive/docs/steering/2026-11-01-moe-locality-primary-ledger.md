## Findings

The locality mechanism is credible; the historical headline is not a transferable performance estimate. The [2024 PyTorch post](https://pytorch.org/blog/accelerating-moe-model/) reports FP16 Mixtral expert GEMMs on A100/H100, roughly18–20% from Split-K and maxima4x/4.4x after scheduling changes. Its M2 profile reports2.7x and fewer loads; the preliminary70% end-to-end claim explicitly accompanies unresolved expert mapping. The post uses both “+254%” and “2.54x” for L2; these are mathematically different, so do not normalize them into a verified multiplier. None is a measured H200 Muse layer result.

## Later work and transferable mechanism

The [August2025 PyTorch grouped-GEMM post](https://pytorch.org/blog/accelerating-moes-with-a-triton-persistent-cache-aware-grouped-gemm-kernel/) is a distinct BF16 workload. Scheduling-only1.33x/+60% L2 is for eight groups with M4096,K2048,N7168. Up to1.50x combines persistence, ordering and TMA against a Triton baseline;2.62x refers to a manual PyTorch loop in DeepSeekv3 training/FSDP2 on8H100. These are different denominators. Its device-created expert descriptors require private slots and proxy synchronization. Do not transfer its numerical results to packed NVFP4 kernels.

The blog-linked torchtitan directory can be pinned to [a32f0df21b8791f27543c512f446b5b004612013](https://github.com/pytorch/torchtitan/tree/a32f0df21b8791f27543c512f446b5b004612013/torchtitan/experiments/kernels/triton_contiguous_group_gemm) (May1,2025); `cg_forward.py` blob `68553e08ae54261d276d55029b602e40858e9cc3` contains a shortened-final-M-group mapping and persistent stride. It assumes expert-contiguous aligned token blocks. This is a reproducible source landmark, not a claim that it is the blog chart's exact benchmark commit. The blog's [vLLM integration19443](https://github.com/vllm-project/vllm/pull/19443) is also closed/unmerged, head `1ffbecb48b7da99c2a85557ddbb340244d784af8`.

Distinct transferable hypothesis: reorder existing expert output tiles within a bounded M-row band to shorten reuse distance of the SAME packed expert-weight N/K tile, without changing reductions, tile shapes or persistence. This is logical work order, not physical column-major storage, not another Split-K proposal. It helps only when one expert has multiple M tiles reusing those weights; a single M tile per expert has no such cross-M reuse. First enumerate the actual native scheduler and routed M-tile multiplicities under fixed legal routing; root owns mapping to current G/owned kernels and prior losers. No schedule experiment is justified by this article alone.

## Tests, acceptance and stopping

`tools/test_moe_locality_map.py` is an independent CPU integer proof, not borrowed kernel code. Four tests pass: all1..32 rectangular grids map bijectively after correction; square grids hide the original defect; non-square negatives fail; padded allocation tail preserves each valid expert tile exactly once. Example grid8x448: the original mapping has only64 in-range M assignments among3584 programs. This demonstrates skipped work, not any actual measured GPU speedup.

Before a native schedule change: prove complete per-expert tile ownership including final groups, top-k repetition/padding and empty experts; preserve barriers and packed scale layouts; match FP32 plus intended BF16 boundaries and all cache writes; then require independent-build/null-controlled whole-layer or official-score gain on representative routing. Stop if there are no repeated M tiles, if an equivalent ordering already lost without new evidence, or if timing improves through incomplete coverage. No projected speedup or top10 conclusion follows from these sources. Remaining gaps: exact chart commits, corrected-version H200 performance, X attribution, and native routed-tile reuse/traffic profile.
