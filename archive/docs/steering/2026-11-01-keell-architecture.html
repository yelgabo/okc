03 / MoE is the main architectural investigation

The core math is shared: route tokens → gate/up projection → SwiGLU → down projection → per-expert normalization and weighted aggregation. The meaningful differences concern how work is partitioned, how intermediate results become ready, and which consumers must wait.

Owned mode 51

Setup and cost modelWarp scans, job metadata, stage-cost tables. Warp-parallel stage searches already exist in our source.
Phase A: owned unitsAvoid stream-K fixup when a CTA owns a whole unit. Publish readiness for dependent phase-B work.
Phase B: claimed workDynamic work claims trade balancing against claim overhead and the final wave.
Completion / final aggregationMode 51 uses the final-pass sum-of-squares strategy at M≥64; below that it keeps the smaller-M epilogue policy.

External WGS + SC6 + MFIN

Parallel work-range preparationWeighted contiguous stage ranges for both phases; producer computes ranges while consumers gather.
Four consumer warpgroupsRS-WGMMA, TMA weight ring and activation ring; partial units use stream-K fixup and designated completion policies.
Compressed scale bytesLossless six-bit scales in WGS weight stages, gated by actual scale-byte values during prepare.
Per-expert completionMFIN publishes expert completion counters. A token's final pass waits for its relevant local experts rather than a full-grid completion barrier.

Completion scope: why MFIN can matter

This is a replacement synchronization protocol, not permission to remove a barrier. The external implementation includes deferred publication, acquire polling, per-launch generation/parity storage and cleanup logic. An owned version needs a producer-store → release → acquire → consumer-read proof, safe reuse across graph replays, and a progress argument.

One stage falls from 36,864 to 35,840 bytes: a 2.78% total traffic reduction, or a bandwidth-only speedup ceiling of 1.0286× for that weight traffic. It cannot explain an 11% whole-layer score gap by itself. Reconstruction cost, alignment and overlap still determine the result. The source verifies scale bytes are in 0x40…0x7F; subtracting 0x40 then packing six bits preserves every scale exactly.

05 / Projection, attention and prefill


Projections: the base idea is shared; large-T selection differs


Both implementations use lossless dense-weight encodings and shape dispatch. Their published layer adds chenwainuo-derived rq plans at QKV128, QKV256 and unpooler128, and pins library plans elsewhere. In the external receipt, preparation selected rq:d2s5hzwP at QKV128 and unpooler128, and rq:n256s5m1hzmEH at QKV256. Their combined QKV/unpooler128 profile is 30.7 µs; our recent control's corresponding grouped library row is 30.2 µs. Kernel-family names alone do not establish a win.


Their README reports exact-file projection check 1.5742× and submit 1.5690×, below their 1.5876× public row. Against our 1.527806× best, those represent roughly 3.04% and 2.70% differences, not the 3.91% best-row comparison. Our owned QKV depth-two and cyclic-push-epilogue tests already lost (4542b2b04cb344ec, 4edaa20c98904404). The newer owned Lt transfer 1e3349e377234e89 passed a two-verify-load screen; full combined confirmation remains a separate gate.


Attention: inspect active compile flags, not just comments


Their standalone attention file adds ZhimaoL-derived verify paths: balanced full-context WST for the enabled batch range and VP2 for batch-one sliding verification, with a vjeux-derived path elsewhere. Our current attention has its own one-launch cluster / split-KV and warp-specialized full-context path.


The published standalone file says “MEASUREMENT BUILD ONLY … never submit.” Although the C++ defaults ZH_SCH to zero, its active Python build flags explicitly pass -DZH_SCH=1 to both verify extensions (lines 5710 and 5722), enabling the piecewise-linear exponential paths. Treat this file as a diagnostic comparator until the exact active math has been independently validated under our precision policy. The checked external layer file is separate and has no ZH_SCH switch; do not transfer this finding to its passing layer receipt.


The README reports same-box attention screens of 2.63–2.66× versus a 2.7168× best row. No fresh standalone check or controlled owned/external attention comparison was run for this audit. The board gap is not a validated transferable gain.


Prefill: the largest score difference, with weaker source alignment


Their published prefill combines tuned cuBLASLt projections, ZhimaoL-derived FMHA with an N72 P·V layout, and persistent experts. The N72 tensor-core output layout incorporates softmax-row-sum work into the P·V formulation. Their README also lists a fresh-thread/default-stream routing defect. Our current muse_prefill_layer/submission.py is the plain PyTorch starter with per-call expert dequantization; it is not established as the source of our historical 1.2166× public best. Prefill was deferred in the current campaign, so its large score gap is not evidence that the four active kernel tracks lack all these mechanisms.


06 / Performance eligibility and what to do next


A newer concurrent fork audit found issues that the passing upstream check does not settle. Its generator disables deferred T1 normalization and restores explicit BF16 activation/projection/branch rounding; moves short-boundary carry/tail reads after the PDL wait; disables the invalid captured-output diagnostic; and isolates attention scratch and per-call prefetch state. These are material constraints on how much of the raw 2.2488× transfers. The original public file is a performance reference, not a validated drop-in under our precision and ordering policy. See the live fork handoff and the fork generator. This report preserves the original comparison rather than silently comparing an unmeasured corrected fork.
