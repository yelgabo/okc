## Capture legality and lifetime consequences

1. **Active capture attachment is supported.** Driver cuStreamGetCaptureInfo supplies a process-lifetime-unique capture ID and borrowed graph. Its graph_out contract permits graph operations except destruction/node removal while capturing. cuGraphRetainUserObject only creates/moves references; it adds no execution node or dependency. Together these documented contracts support resource attachment immediately before the actual Lt reader submission. Only CUDA_SUCCESS plus ACTIVE validates ID/graph; invalidated capture, query error or failed retain must stop before an unowned compressed pointer is submitted. The API can return previous asynchronous errors. Never treat error as ordinary eager mode. Exact header/versioned signature, context and current stream are required; no reuse of old ctypes signatures.
2. **The graph, not Python, owns the attached reference.** Guide6.2.8.7.4 explicitly covers clone multiplicities and instantiation. GraphExec destruction while work is pending defers reference release until execution completes. Thus losing the original prepared state cannot free a mapping still retained by those graph references. The helper need not discover the private evaluator's last replay or install a destruction hook there.
3. **Update semantics are explicitly covered, not guessed.** Whole executable updates and executable child-graph replacement clone the new source references, replace the old set, and defer old releases through pending launches. Child graph references belong to the child. All replacement source graphs containing this PR must also pass the attachment hook. Arbitrary external node-pointer edits or manual removal of user references are outside this construction; no resource mechanism protects intentionally stripping its ownership. A clone created before attachment is not retroactively protected: attachment must precede any reader capture completion/instantiation/clone exposure that could escape. The actual reader must hook every compressed plan, including independently prepared/copied owners, not just one observed shape.
4. **Abort is not a reason to free the borrowed graph manually.** Stream API says the graph is transferred or destroyed at EndCapture; invalidation returns a NULL graph and errors until EndCapture. Combining destruction with graph-owned user references supports release of aborted capture refs; this is a documented-contract inference, not a tested callback timing result. Graph may become invalid before EndCapture. Do not revisit its cached handle, call graph release on it during error unwind, or release a moved caller reference twice. If a caller never ends an invalid capture, timely destruction is not promised; do not claim bounded cleanup for such caller misuse.

Capture IDs avoid graph-handle reuse errors, but a dedup entry may be committed only after retain succeeds. Multiple retains are valid if balanced by CUDA graph lifetime; unbounded host registries are not required. Graph objects are not thread-safe: this source proof assumes graph operations follow a valid serialized capture sequence. An adapter mutex alone does not serialize unrelated caller graph edits. No undocumented cross-thread graph mutation permission is inferred.

## Ownership and cleanup proof obligations that remain real

- Keep separate accounting for host/tensor ownership, manually owned CUDA user references, graph-owned references and any pending eager GPU uses. Driver flags0 adds graph references; MOVE transfers existing caller references. Releasing a reference the caller no longer owns or using a dead user-object handle is undefined. Tensor/view ownership and graph ownership must converge on the same backing resource without a cycle where the backing owns the last caller user reference whose callback is needed to destroy that backing. An ownership control handle and callback payload may be distinct; exact implementation must prove its graph.
- The CUDA destructor callback must only perform a bounded one-way CPU handoff. **No direct or indirect CUDA call:** dropping the last shared_ptr inside the callback is wrong if its destructor synchronizes/unmaps/releases a CUDA context. No join, queue-space wait, CUDA completion wait or wait for helper acknowledgement. A mutex/queue design must prove that the helper cannot hold a lock while waiting for CUDA which is waiting for the callback. Callback enqueue failure needs a pre-established nonblocking policy, not allocation failure followed by immediate CUDA cleanup.
- A separate cleanup thread is expressly allowed only without a reverse progress dependency. It must own valid context access and resource records until cleanup, and the callback's executable code, queue and helper must outlive delayed callbacks. A host context lease may protect against ordinary premature primary-context teardown; it does not survive arbitrary device reset/process shutdown by magic. Joining the helper from a callback or destructor while a required host reference is still outstanding creates a cycle. These lifecycle details are not supplied by the Guide example.
- CUDA graph references cover captured work, **not eager Lt launches or the preparation bit-copy**. A host call must hold the owner while enqueueing; final cleanup must also cover already submitted eager/copy uses. A separate thread context completion step can cover those preceding uses after all possible eager host owners have retired. It must not be called by the CUDA callback. Failed completion/context errors must not authorize unmap. Pre-copy unpublished construction failure can unwind independently; after capture attachment, leave graph references to CUDA rather than forcibly reclaiming them.
