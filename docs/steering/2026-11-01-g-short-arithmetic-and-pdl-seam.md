## Outgoing-only protocol and progress proof

Decoded helper0 `moe_fused` lines2202 onward: entry `griddepcontrol.wait`, helper-role dispatch, route/phase computation, `WS_JOIN` at2405, outgoing trigger2409, then grid-counter/finalizer work. There is no compute-role early return skipping the trigger in the selected kernel; helper warps return after their obligations while compute threads trigger once per CTA. Empty local work still falls through the join/trigger/finalizer. The trigger is **not** final BF16 expert-output readiness.

The selected SK2 consumer already has the right separation. Lines109-113 preissue immutable weight stages, not expert-output X. CL1 barrier/table setup follows; after CTA synchronization, every thread executes `griddepcontrol.wait` and `fence.proxy.async.global` at148-149 before tid0 issues X TMA at151-152. Producer refills occur after this point. Preserve the fence as well as the dependency wait. Weight/escape metadata and descriptors must remain immutable with captured storage lifetimes; constructing a descriptor from a pointer is not reading the unfinished X values.

Minimal proposed source protocol, **not applied**:

1. Keep route -> expert full completion, checked cooperative expert launch, grid size/resource checks, current arithmetic and reader-release protocol.
2. Keep the existing expert outgoing trigger, grid join and BF16 final output stores unchanged. No expert thread waits for unpool.
3. For role `un` and only T1/T8 `slice8_r192`, enable the secondary's programmatic launch attribute and its existing pdl argument/preamble. Retain current default two-stage, zero-pacing policy; no stage sweep. Make this launch-scoped/private-state-safe, not a global PDL setter leaking to other roles or graph captures.
4. Keep every X read after dependency wait plus proxy fence; final boundary remains ordinary completion. All other PDL/GLE edges stay OFF.

Dependency DAG: completed route -> admitted expert CTAs -> each CTA trigger -> optional unpool independent preamble; expert finalization -> expert completion -> unpool wait return -> proxy bridge -> X TMA -> unpool completion -> final boundary. No back-edge to expert exists. CUDA only permits early dependent scheduling after every primary CTA has triggered/completed. Thus this does not require admitting missing expert CTAs after unpool occupies slots. If no resource overlap exists, consumer launch can be delayed; producer still finishes without it. This removes the specific co-residency cycle risk of a successor needed by a blocked producer. It proves a source dependency structure, **not** that CUDA will overlap these particular cooperative/graph nodes or that resources permit useful concurrency.

For incoming route -> cooperative expert PDL, this audit establishes neither a universal API prohibition nor a complete safe restoration. The exact admission/graph semantics of a cooperative secondary behind unfinished route CTAs, plus every proxy read and deferred GLE carry, need proof. That unresolved combination is bypassed, not silently accepted, by the outgoing-only proposal.

Primary authority read November2 UTC: [CUDA13.0 guide 6.2.8.6](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-c-programming-guide/index.html#programmatic-dependent-launch-and-synchronization) permits a normal primary and programmatic secondary, requires all-primary-block trigger participation, and warns overlap is opportunistic. [PTX9.0 griddepcontrol](https://docs.nvidia.com/cuda/archive/13.0.0/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-griddepcontrol) says repeated per-CTA triggers add no effects; wait covers prerequisite completion and memory visibility. These are primary API/order references, not measured exposure evidence. Existing fork precision and ordering reports retain the rules/baseline authority; no new eligibility ruling is made here.
