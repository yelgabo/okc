# G-fork precision contract: requirements versus conservative policy

November1,2026. Read-only audit; no kernel changes, implementation, GPU dispatch, public proposal, organizer contact or post. Root evidence checkout `06c1a53886067a6363de7633946c8870dfba6e9a`. Read the fork safety/projection audits, dense stock budget and current607e dense-ROI closure first. This narrows their contract language; it does not reopen their experiments.

**Finding:** calling every BF16 split partial categorically forbidden overstates the published rule. The rs128/opaque-Lt split bans are conservative policy choices under unresolved internal-reduction scope. BF16 boundaries before another operator/nonlinearity have substantially stronger interface support. MFIN fall-through and unproved ordering are separate correctness defects and remain disabled/fenced. No newly eligible release or meaningful measured speedup follows.

## Important active-backend distinction: router input

Do not infer a universal BF16-upcast router input from a fallback implementation. Pinned [JIT C++ norm boundary](https://github.com/sgl-project/sglang/blob/a55ab7d5ae1bba59ac351e55026fe7f7644ecc5f/python/sglang/kernels/jit/csrc/muse_spark_v12/norm_residual.cuh#L246) stores a BF16 branch output while its router vector receives the unrounded FP32 normalized value when pre_norm_bf16 is false; the cluster path does the same at589–607. Baseline317–328 calls that boundary without pre_norm_dtype, then FP32 F.linear at T<=8. This supports the existing FP32 short-router interface. In contrast the [Triton path](https://github.com/sgl-project/sglang/blob/a55ab7d5ae1bba59ac351e55026fe7f7644ecc5f/python/sglang/kernels/ops/muse_spark_v12/fused_norm_residual.py#L144) writes a BF16-rounded FP32 router copy, and Python native also casts through output dtype. These implementations are numerically distinct. They must not be silently relabelled bitwise equivalent, nor does the FP32 router path authorize feeding FP32 h to the BF16 pooler. GLE_FRT and disabled GLE_T are distinct paths.

## Why an all-FP32-partials ban cannot be inferred from BF16 operands

Pinned [PyTorch2.10 documentation](https://github.com/pytorch/pytorch/blob/v2.10.0/docs/source/notes/cuda.rst#L235) says BF16 reduced-precision reductions are permitted by a default flag and can be disabled. [NVIDIA's GEMM numerical-behavior documentation](https://docs.nvidia.com/cuda/archive/12.8.1/cublas/index.html#gemmex-algorithm-numerical-behavior) separately describes split-K reduction and the control that disallows reduced-precision reductions. Thus BF16 operands/FP32 MMA accumulation do not uniquely specify every reduction/storage operation. This is evidence against a blanket inference, not proof that a particular judged cuBLAS kernel uses BF16 partials, nor contest approval of rs128. Actual selected baseline algorithms, reduction modes and runner flags were not measured here. The source allows F.linear fallback; no local runner evidence establishes an additional contest-wide all-partials-FP32 mandate.
