## Numerical and format obstructions, independently witnessed

[Own CPU proof](evidence/2026-11-02-research-flute-engine-screen/proof.mjs) imports only Node built-ins, never donor modules or target APIs; [result](evidence/2026-11-02-research-flute-engine-screen/cpu-proof.json).

1. **Group16 cannot simply be relabeled group64.** One legal64-weight block with four scales1/1.125/1.25/1.375 (E4M3 bytes38/39/3a/3b), each containing all16 E2M1 codes, needs **57 distinct exactly representable BF16 products**. A single group64 scalar times a16-entry codebook has at most16 distinct values, even permitting code remapping and an arbitrary codebook. Thus default pack/wrapper conversion cannot preserve this block. Adding group16 to CUDA/configuration is substantive source work, not a template selection. Legal lossless compressed repacking remains possible in principle; persistent BF16-expanded weights remain barred by TASK.md:102, as P2 established.
2. **Mixed reduction changes a required boundary.** config.hpp:197-198 selects FP32 MMA accumulation but BF16 fixup storage. qgemm_kernel.hpp:719-751 converts partials before Stream-K reduction. FP32 partials257 and-256 sum to1; rounding each to BF16 first produces0. This is an algebraic counterexample, not a measured Muse failure. Changing to High would change the published generated policy; source enum availability is not evidence that the exact caller selects it.
3. **Post-dot globals must precede BF16 output rounding.** FLUTE has no such argument/epilogue operation. For dot257 and FP32 global1.125, BF16(dot*global)=290, while BF16(BF16(dot)*global)=288. A wrapper multiplying the already-rounded output is not equivalent; folding globals into block scales is not automatically equivalent either. Both gate and up must independently cross the scaled BF16 boundary, then FP32 SiLU/product becomes BF16 inter. Down likewise scales then rounds before FP32 gamma multiplication. Full4096-output per-expert RMS with eps1e-8 occurs **before** slot-weighted FP32 combine/final BF16. Neither FLUTE linear forward nor its optional Hadamard path implements these Muse semantics; changing basis is not a free adoption step.
