## Contract and documented route

Official challenge frontend bundle index-D8JLIOgd.js explicitly permits prepare-time weight repacking/lossless compression and inline native compilation, and forbids harness/timing tampering, output replay and lower precision. Its /rules HTML has no readable rule body; evidence pins the actual public JS SHA and extracted sections. Existing docs/context.md:93 likewise places compiling/repacking in untimed prepare. Per-allocation independent immutable weight copies fit that model **in principle**; no global allocator replacement, environment flags, supplied-tensor mutation or data/output cache is acceptable.

PyTorch2.14 CUDA notes document CUDAPluggableAllocator plus MemPool/use_mem_pool for scoped allocation. NVIDIA Hopper §1.4.2.3 and VMM §4.17.5.2 document requesting generic compression, checking device support and verifying actual handle properties; request success alone is insufficient. Neither support nor compression of these BF16 distributions is known. No capacity-footprint reduction is promised. Primary URLs, retrieval hashes and statuses are pinned in evidence; PyTorch v2.14.0 resolves commit2b3ec34829036a65cd9d1398ea72a0167dc37470.

**Important ABI finding:** memory.py's free-function docstring omits the device argument. The same-version C++ CUDAPluggableAllocator.h:20–21,152 and .cpp:139 require **free(void*,size_t,int,cudaStream_t)**, consistent with the CUDA-notes example. Do not implement the three-argument docstring. Allocation receives size/device/stream; use exact installed ABI before any later implementation. This is a resolved documentation inconsistency, not a reason to reject scoped pools.

The allocator constructor dynamically loads a .so path. A host-only adapter generated from inline source during prepare, using the standard documented extension build/load path, is materially different from reading external data or files during kernel_fn. **The public rules do not explicitly adjudicate this allocator loader.** Thus this report does not certify checker/organizer acceptance. If that loading mechanism is prohibited, STOP this particular adapter route; do not evade the restriction with undocumented tensor storage, callbacks into private APIs, prebuilt sidecars or harness changes. Source inspection finds no inherent contradiction in private-copy allocation; target library/checker compatibility remains a capability gate.

## Minimal future adapter/lifetime design — no implementation

One inline C++ host translation unit, CUDA driver/runtime headers and driver linkage, exported C alloc/free and host status accessors; no CUDA device source or changed kernels/math. Its allocation records holddevice, reserved VA, rounded physical/mapped size, handle, requested/actual properties and allocation type. Set current device/context correctly; no C++ exception may cross the C callback ABI.

1. Capability stage checks VMM support and GENERIC_COMPRESSION_SUPPORTED. Build device-local PINNED allocation properties with compressionType GENERIC; get minimum granularity, safely round callback segment size, reserve aligned VA, cuMemCreate, verify cuMemGetAllocationPropertiesFromHandle, map and grant device read/write access. Preserve128Bweight alignment and original contiguous shapes/strides. Check every return value; unwind each partially completed resource in reverse order.
2. Create a dedicated MemPool from the public pluggable allocator with use_on_oom=False. Enter use_mem_pool only around one PR empty_like/bitwise copy on the preparation thread, outside capture; exit before any normal tuning/scratch allocation. Do not wrap threaded normalprepare: use_mem_pool only affects the current thread. Caching may request segments larger than the tensor; verify every backing handle/range, not just a requested75.5MBtensor size. Unsupported capability, nongeneric actual property or incompatible pool/allocator means discard treatment and retain the ordinary original state; never report plain backing as generic. Failure/OOM must surface safely through the supported allocator contract, not become a null-pointer tensor or uncaught C callback exception.
3. Insert the private PR owner **before _graft_lt_plan installs its twoPR plans and before any graph that uses those plans is captured**, after ordinary rawPRconstruction. Preserve all other state, compile flags, Lt picks and inputs. Do not only replace st.pr after plans/captures already saved its old pointer. Plans must both hold the new tensor. This is an explicit future source integration point, not an edit to today's candidate.
4. Prepared state retains the new tensor, pool, allocator, loaded DSO and host allocation registry for every graph replay. Reading persistent weights during capture requires no pool scope in kernel_fn. Tensor+graph/state lifetimes must prevent reuse/unmap; do not assume an external-pointer graph automatically owns its tensor. Copy completion precedes first consumer; preserve existing streams/fences. After graphs and all dependent GPU work are finished, release tensor/plan owners and pool; free unmaps, releases physical handle and returns reserved VA on its owning context. No cleanup, host synchronization, file operation or capability branch inside timed calls. Failure rollback leaves supplied tensors/default allocator unchanged.

### Concrete supported interface and ownership

PyTorch's public C++ creation documentation explicitly supports externally allocated CPU **or CUDA** data via from_blob and says that these tensors cannot be resized. The immutable v2.14.0 header at commit 2b3ec34829036a65cd9d1398ea72a0167dc37470 provides **at::from_blob(void*, IntArrayRef sizes, std::function<void(void*)> deleter, const TensorOptions&, std::optional<Device> target_device)**, plus explicit-strides and storage-offset overloads. No private storage setter or allocator registration is needed. This is documented external-buffer use plus a concrete public-header owning-deleter overload, not a documentation example specifically certifying compressed VMM interoperability.

The pinned implementation creates a DataPtr with the supplied callable, stores it in non-resizable Storage, and sets contiguous strides when omitted. InefficientStdFunctionContext retains the callable and invokes it on context destruction. A callable capturing a shared RAII mapping owner can therefore keep VA, handle, mapped length and context alive with tensor storage; tensor/view/plan references sharing that storage retain it. Do not confuse this deleter ownership with caching-allocator ownership. Return the normal Tensor through the existing extension's host binding; adding that binding and Driver linkage is still a native-host addition even though device-kernel bodies remain unchanged. Installed libtorch/header/ABI compatibility remains untested.

TensorOptions must specify BF16, correct CUDA device and no autograd; the overload's explicit target_device can also identify that same actual allocation device. The implementation checks indexed options against the resolved/provided device; a tag neither moves data nor proves the pointer was correctly mapped. The adapter must establish the real mapping/device/access itself. Preserve logical [4608,8192], strides [8192,1], offset0, 75,497,472 logical bytes, suitably aligned base and sufficient granularity-rounded backing. Do not resize or use a conversion/clone as a replacement for the backing. A same-dtype, same-device bit copy in prepare is required, with completion ordered before every first reader; no numerical conversion, cached outputs or supplied-tensor mutation.

### Stream, graph and teardown obligations — not supplied by from_blob

**The deleter is void(void*), not a stream-aware free callback. Last host reference is not GPU completion.** RecordStream.cu dispatches to CUDACachingAllocator::recordStream; the pinned native caching allocator explicitly returns for a DataPtr whose deleter differs from local_raw_delete. from_blob uses deleteInefficientStdFunctionContext instead. Thus tensor.record_stream is not a retirement solution for this direct external allocation on that backend; other installed backends cannot be assumed to supply one either. No source proof here establishes that a captured graph owns an arbitrary external tensor.

A sufficient conservative ownership design is: prepared state and both Lt plan objects retain the returned tensor, with an explicit mapping/state owner retained for the entire lifetime of every graph using it. Install **before** the two PR _graft_lt_plan calls/captures, not by replacing state.pr after pointer capture. Copy on the preparation/consumer stream or establish the explicit dependency. Never mutate mapping/address after capture. On final retirement, prevent new launches/replays, finish all previously submitted readers on the owning CUDA context outside timed/captured execution, then drop graph/plan/state references and unmap the complete mapped range, release the retained handle, and free the matching VA reservation. NVIDIA documents cuCtxSynchronize as waiting for preceding context tasks: this is sufficient only with the no-future-submission ownership condition, not as permission to destroy storage while a reusable graph remains live. One copy-completion event does not cover later replay readers.

The owner/deleter must be no-throw, context-correct, single-release and rollback-safe. Partial reserve/create/map/access/wrap failures unwind only completed resources; property mismatch leaves the normal PR and subsequent plans unchanged. Context teardown, asynchronous errors, exception paths and owner/graph destruction order require explicit integration policy: do not unmap after a failed completion proof, silently ignore errors, or rely on process exit as normal cleanup. An explicit retirement method plus final deleter safety net is a design option, not implemented or tested here. Supporting APIs exist; the actual harness state/graph retirement integration remains a gap.

### Simpler allocation, different responsibilities

Direct ownership removes CUDAPluggableAllocator's DSO-path constructor, C callback ABI, allocation registry/pool-segment indirection, private MemPool object and thread-local use_mem_pool scope. One exact PR allocation makes requested versus actual backing attribution simpler. It retains all original capability/granularity/property checks, driver resources, one extra private PR copy, source/host-extension loading and numerical/ordering obligations. It **adds no automatic caching-allocator accounting or stream retirement**. PyTorch's official memory documentation explicitly says direct cuMemCreate allocations are not visible to its memory profiler; allocator statistics/snapshots cannot establish actual backing/compression or safe capacity. Rounded physical memory remains consumed, may affect OOM/capacity outside allocator limits, and is not freed by empty_cache. No footprint or bandwidth benefit is inferred.

Eligibility is unchanged in substance: independent prepare-time weight copying/repacking has a rules basis in the earlier pinned rules bundle; no global allocator, supplied tensor, timed path, harness or data-I/O alteration is needed. The public rules do not explicitly bless this host VMM binding. Removing the pool loader resolves that particular implementation concern, **not** checker/organizer acceptance. Do not call API availability contest admissibility. Verify installed capability and actual GENERIC allocation property, cleanly STOP/fallback otherwise; successful property still does not prove compressibility, correctness through replay or useful speed.

**Revised ONE future distinguishing question (not a request to run):** can a public from_blob owning-deleter tensor over one actual GENERIC VMM PR mapping preserve BF16 bits, exact device/stride/address and both plan references across the real graph lifetime, with documented no-future-use retirement and unchanged supplied/default allocations? This replaces the pool-specific capability question. A positive would settle only that adapter's capability/ownership integration; it would not settle useful compression, challenge eligibility or end-to-end speed. Long-PR-only six-load sensitivity stays conditional: 1% layer-factor improvement needs 2.940985% whole-latency reduction on both affected loads, with other loads unchanged. No measured exposed fraction has appeared. Serial has no favorable terminal signal per current user; the last check stays reserved.
