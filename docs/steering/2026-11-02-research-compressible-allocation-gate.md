## Contract and documented route

Official challenge frontend bundle index-D8JLIOgd.js explicitly permits prepare-time weight repacking/lossless compression and inline native compilation, and forbids harness/timing tampering, output replay and lower precision. Its /rules HTML has no readable rule body; evidence pins the actual public JS SHA and extracted sections. Existing docs/context.md:93 likewise places compiling/repacking in untimed prepare. Per-allocation independent immutable weight copies fit that model **in principle**; no global allocator replacement, environment flags, supplied-tensor mutation or data/output cache is acceptable.

PyTorch2.14 CUDA notes document CUDAPluggableAllocator plus MemPool/use_mem_pool for scoped allocation. NVIDIA Hopper §1.4.2.3 and VMM §4.17.5.2 document requesting generic compression, checking device support and verifying actual handle properties; request success alone is insufficient. Neither support nor compression of these BF16 distributions is known. No capacity-footprint reduction is promised. Primary URLs, retrieval hashes and statuses are pinned in evidence; PyTorch v2.14.0 resolves commit2b3ec34829036a65cd9d1398ea72a0167dc37470.

**Important ABI finding:** memory.py's free-function docstring omits the device argument. The same-version C++ CUDAPluggableAllocator.h:20–21,152 and .cpp:139 require **free(void*,size_t,int,cudaStream_t)**, consistent with the CUDA-notes example. Do not implement the three-argument docstring. Allocation receives size/device/stream; use exact installed ABI before any later implementation. This is a resolved documentation inconsistency, not a reason to reject scoped pools.

The allocator constructor dynamically loads a .so path. A host-only adapter generated from inline source during prepare, using the standard documented extension build/load path, is materially different from reading external data or files during kernel_fn. **The public rules do not explicitly adjudicate this allocator loader.** Thus this report does not certify checker/organizer acceptance. If that loading mechanism is prohibited, STOP this particular adapter route; do not evade the restriction with undocumented tensor storage, callbacks into private APIs, prebuilt sidecars or harness changes. Source inspection finds no inherent contradiction in private-copy allocation; target library/checker compatibility remains a capability gate.

## Minimal future adapter/lifetime design — no implementation

One inline C++ host translation unit, CUDA driver/runtime headers and driver linkage, exported C alloc/free and host status accessors; no CUDA device source or changed kernels/math. Its allocation records holddevice, reserved VA, rounded physical/mapped size, handle, requested/actual properties and allocation type. Set current device/context correctly; no C++ exception may cross the C callback ABI.

1. Capability stage checks VMM support and GENERIC_COMPRESSION_SUPPORTED. Build device-local PINNED allocation properties with compressionType GENERIC; get minimum granularity, safely round callback segment size, reserve aligned VA, cuMemCreate, verify cuMemGetAllocationPropertiesFromHandle, map and grant device read/write access. Preserve128Bweight alignment and original contiguous shapes/strides. Check every return value; unwind each partially completed resource in reverse order.
2. Create a dedicated MemPool from the public pluggable allocator with use_on_oom=False. Enter use_mem_pool only around one PR empty_like/bitwise copy on the preparation thread, outside capture; exit before any normal tuning/scratch allocation. Do not wrap threaded normalprepare: use_mem_pool only affects the current thread. Caching may request segments larger than the tensor; verify every backing handle/range, not just a requested75.5MBtensor size. Unsupported capability, nongeneric actual property or incompatible pool/allocator means discard treatment and retain the ordinary original state; never report plain backing as generic. Failure/OOM must surface safely through the supported allocator contract, not become a null-pointer tensor or uncaught C callback exception.
3. Insert the private PR owner **before _graft_lt_plan installs its twoPR plans and before any graph that uses those plans is captured**, after ordinary rawPRconstruction. Preserve all other state, compile flags, Lt picks and inputs. Do not only replace st.pr after plans/captures already saved its old pointer. Plans must both hold the new tensor. This is an explicit future source integration point, not an edit to today's candidate.
4. Prepared state retains the new tensor, pool, allocator, loaded DSO and host allocation registry for every graph replay. Reading persistent weights during capture requires no pool scope in kernel_fn. Tensor+graph/state lifetimes must prevent reuse/unmap; do not assume an external-pointer graph automatically owns its tensor. Copy completion precedes first consumer; preserve existing streams/fences. After graphs and all dependent GPU work are finished, release tensor/plan owners and pool; free unmaps, releases physical handle and returns reserved VA on its owning context. No cleanup, host synchronization, file operation or capability branch inside timed calls. Failure rollback leaves supplied tensors/default allocator unchanged.

## Opportunity, cost and smallest discriminator

Initial scope is PR only on verify16/verify32 (T128/256), both contexts:1/3 of the six-load layer score weight. With **actual whole-endpoint** reductiond on both loads and no other changes, layer factor=(1-d)^(-1/3). A1%factor requires2.940985%whole-load shrink;3%requires8.485834%. If net exposed PR fraction isf and its service reductionr, d=f*r only under the additional no-offset/no-overlap assumption; otherwise subtract integration effects. f and r are unknown. No Gaussian-compressibility assumption, peak-bandwidth estimate, grouped nvjet total or profiler activity duration supplies them.

Owning607 long profiles show accepted Lt library activity alongside dominant MoE and context-dependent attention. Aggregated kernels/call counts do not isolate PR's critical-path exposure. PR physical size establishes scope, not DRAM traffic saved. Cold replay still reads unchanged logical values; allocation attribute is not an actual compression-ratio observation.

Cost: one host adapter+driver linkage/ABI, one extra75.5MBprivate PR copy plus granularity/cache overhead, mapping/property checks, preparation time and explicit ownership integration. Footprint is not reduced. This is less numerical/native-kernel redesign than parked G2/scalar/SiLU work, but more setup/eligibility/lifetime risk than the already allocated serial selector. It does not displace that measurement and does not establish a>=1%opportunity. Unsupported/no attribute is a clean STOP, not an invitation to a compiler/readiness loop.

**ONE smallest future distinguishing target question, not a check request:** can the installed judge stack create and retain an independently copied, bit-identical BF16 PR tensor through the public scoped-pool route with every actual backing handle reporting GENERIC, default/supplied allocations unchanged and stable-address graph reads? A negative ends this adapter route before performance work; a positive resolves only capability/integration, NOT useful compression or end-to-end speed.
