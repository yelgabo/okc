## Decision

**Physical/source-level answer: YES, a single8192B fragment can alias a specifically reserved final weight-ring slot without extra shared allocation or a new cross-CTA wait. Merely calling the slot retired is unsafe.** A bounded construction below needs all512 original empty arrivals withheld, the weight-producer warp retained/reworked, two544-thread named-barrier rendezvous, and one already allocated unused mbarrier for completion. It temporarily withholds one ring slot and serializes NTT-1 fragment epilogues. It is not the current implementation and has not passed compilation/resources, PTX implementation review, correctness or timing.

**Allocation answer: NO production/kernel implementation budget on this evidence alone.** Only the last fragment can overlap the next segment's compute. Preserving current doneA publication timing further limits the window to the first stage's existing deferred-flush point, ci4, not two whole stages or the full next expert. NTT1 remains potentially interesting; no structural proof says it cannot win. But we have no selected-route NTT/split frequency or measured exposed SiLU time inside that window. This report closes the unsafe unchanged-producer/unchanged-publication alias and does not establish a material top100 mechanism. A concrete narrow protocol is supplied so the remaining question is discriminating, not generic stitching. No global-buffer replacement, geometry/cap sweep or implementation is proposed/authorized.

## Counterexamples that close the naive protocol

1. Current code releases all512 BW_E arrivals at lg3, before terminal accumulator retirement. An adversarial valid schedule lets producer issue q+3 into q%3 before compute reaches its mailbox store. The slot is now a future operand, not retired storage. Fencing after mailbox writes cannot fix the ownership collision.
2. Current producer returns31 lanes after startup. A544-thread mailbox barrier with unchanged producer waits forever: only513 participants remain (512compute+one weight lane). Reusing WS_JOIN576 also fails because the X producer is independent/other lanes exited.
3. Holding BW_E but asking the weight producer to service the mailbox only after its normal blocking q+3 wait creates a same-CTA cycle: mailbox reader waits slot release; slot release waits reader. Service must happen BEFORE that wait.
4. Asking the X producer to consume pending phase-A epilogues can self-deadlock after it enters phaseB's mf_da acquire loop: the missing doneA publication depends on that same helper doing SiLU. Do not choose the X producer.
5. Leaving original WgsPend kind1 publication unqualified while helper's last fragment still writes xB permits phaseB TMA to read unpublished values. Resource fit does not repair this race.

## Minimal reserved-weight protocol (design only)

Eligible segment: PB=false, exactly16stages, slot<0 (whole unit). Split segments and PB=true keep original code/ordering. Derive scheduling from the same S.wgr/wgs_split iterator as consumers, including phase-A trailing-partial reorder, not `global_stage%16` alone. Let q be the monotonically issued physical sequence of this eligible segment's last stage, r=q%3. q and all producer parity state continue across reorder and A/B boundaries.

1. Keep all32 weight-helper lanes alive in a uniform producer/service loop. Lane0 alone still issues TMA; other lanes participate in mailbox servicing. Initialize S.bars12 with expected32 at startup, alongside existing barriers, before the retained initialization fence/WS_JOIN; do not reinitialize it between units. On each eligible final stage q, retain all original generic-read proxy fences but suppress **exactly its512 BW_E arrivals**. Never suppress another stage's arrivals. Other stages, X retirement and every WGMMA wait/fence remain unchanged.
2. Producer issues at most q+1,q+2 if such work exists (possibly next phase), then services this unit BEFORE waiting/issuing q+3. Existing M<=64 B4 n-2-full pacing remains. Those old full/empty dependencies are satisfied by work already before the consumers' segment endpoint; service does not wait on X/global doneAs or another CTA. Tail with0/1 future stages still enters service, never exits early.
3. All512 compute threads finish terminal wg_wait<0>, retain stage-X retirement/proxy fence, store fragment nt into the8192B slot, then execute required shared proxy fence and `bar.sync 8,544` with all32 weight-helper lanes. The rendezvous establishes all old operand reads and fragment writes before helper reads. Each helper lane loops16 virtual warps, calls the unchanged phase-A epilogue, preserving BF16 gate/up, FP32 SiLU/up multiply and BF16 xB store.
4. For nt<NTT-1, helper finishes that fragment before all544 rendezvous at `bar.sync 9,544`. Only then may compute overwrite the mailbox with nt+1. Thus NTT-1 fragments are unavoidably serialized in this one-mailbox construction.
5. For the FINAL fragment, there is no544-thread ACK rendezvous. Compute can enter the next segment after READY8, retaining a new pending-helper-completion marker and parity in its existing WgsPend register fields. Helper consumes all16 virtual warps while the reserved slot remains untouched; no full-fragment register copy is hidden here. After each helper lane's final mailbox reads/global xB stores, retain/add required shared/global proxy fences. Each lane performs a release mbarrier arrival with **count16** on BW_E+r (32*16=512), replacing rather than duplicating suppressed arrivals, and a count1 release arrival on S.bars[12] (expected32). A helper warp sync precedes its next lane0 TMA issue. No old generic writer/reader fence is removed.
6. At the next segment's existing FIRST/ci=WGSFCI4 flush, every compute thread acquires the expected S.bars[12] completion phase, then executes ORIGINAL kind1 proxy/global fence,128-thread WG barrier and one release increment per WG into mf_da. Do not publish doneA at READY or merely after mailbox loads. For a phase end, the existing terminal wgs_flush performs this acquisition/drain without requiring a next segment. Per-helper-unit epoch parity is separate from weight-ring q/3 parity; do not conflate them or reinitialize barriers each unit.

### Happens-before and progress

Old reads/fences ->544 READY -> helper loads -> helper final shared fence/release-empty -> producer empty acquire -> q+3 TMA is the storage-reuse chain. Helper xB stores -> per-lane global proxy fences ->32 release arrivals -> compute acquire completion -> original WG publication barrier/release -> X-producer doneAs acquire -> phaseB TMA is the output chain. Generic barriers alone do not replace cross-proxy ordering. S.bars12 has one completion phase per eligible unit. Every compute WG must acquire prior helper completion during its next segment (or phase drain) before it can participate in the next unit's544 READY; therefore helper cannot complete two future epochs before a slow consumer observes the old one. No ABA parity shortcut.

There is no new inter-CTA endpoint in either handoff. While compute waits helper completion, helper only reads this mailbox, evaluates arithmetic/stores and arrives locally; it does not wait for compute stage5, X readiness, grid residence or another CTA. While helper waits READY, consumers can reach it using already issued stages through q; no q+3 operand is required. After final READY, compute may wait at ci4; helper can finish independently and unblock both that wait and q+3. This proves absence of the NEW local cycle, conditional on inherited source operations reaching the segment. It is not a fresh proof of the entire kernel's pre-existing global split/grid progress and does not assume co-residency to discharge those inherited obligations.

Split units retain red.global partial adds, release/acquire counts, designated finisher, fixup zeroing and existing epilogue owner. No partial output goes through the mailbox. Empty phase/CTA executes zero matching services/zero completion waits; initialize but never wait on an unproduced epoch. Final eligible A unit must drain before A phase returns, even with no following work. PB=true/B4FIN fixed shuffle tree, global finish barriers, output reads, launch epochs and occupied-to-empty replay stay unchanged. All resource/graph/replay correctness still needs review/testing if implementation is later authorized.

## Overlap and budget: why fit is not a priority win

One mailbox cannot release old accumulators into next-unit WGMMA before all NTT fragments have been copied. It can overlap fragment nt epilogue with subsequent fragment stores only if a separate snapshot is retained; this specific four-float helper protocol does not. NTT-1 fragment epilogues plus2NTT-1 full544-thread rendezvous are exposed between segments. Only final fragment survives READY into next compute. The weight producer issues no more weights while servicing it, so three-slot run-ahead is reduced until release. Worse, retaining existing doneA publication forces next-first-stage compute to wait at ci4 (GS2: five issued commit groups of16k-step pairs, not two whole stages). This is an operation-count window, NOT measured microseconds or guaranteed exposed SFU saving. Last unit has no next-compute window. Split fixup epilogues are untouched. At NTT8 only one of eight equal-size fragments is even eligible for this cross-segment overlap; this is not a time bound. NTT1 avoids earlier-fragment serialization but still pays transfer/barriers/producer service and may lose.
